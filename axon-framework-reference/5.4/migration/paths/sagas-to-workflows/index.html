Saga to Workflow Upgrade

This guide explains how to model an existing saga process as an Axoniq workflow. There is no direct, general-purpose saga-to-workflow conversion. Reconstruct the saga’s state machine, implement the intended behavior with workflow steps, and verify the differences explicitly. Existing instances finish in the legacy saga runtime; new instances start as workflows. It covers behavior conversion, verification, coexistence, and retirement.

The Axon 4 sagas to Axon 5 legacy sagas path covers the preceding compatibility upgrade. Return to the staged upgrade plan for the complete application upgrade.

Prerequisites

  • Run the existing sagas on a compatible Axoniq Framework release and prove they can resume their persisted state. The legacy compatibility route requires version 5.4.0.

  • Complete DCB context preparation for the workflow event store.

  • Resolve legacy deadline, serialization, and token compatibility before changing process ownership.

  • Preserve a baseline of saga source, tests, stored state, associations, and processor identities.

Use the workflow reference for the selected release’s APIs and configuration. Use the saga-to-workflow skill for behavior inventory, implementation, and verification. See installation and usage below. Framework-wide OpenRewrite recipes belong to the earlier code upgrade stage. They do not convert persisted saga state into workflow execution history.

Sagas and workflows

A saga coordinates a process through event handlers and persisted fields. Association values route events to the right instance. Flags, counters, and deadline identifiers describe where the process is and what it should do next.

A workflow expresses the process as a method containing durable steps, waits, branches, and loops. Its execution history records step progress; the workflow body must remain deterministic during replay. Put commands, queries, and external side effects inside steps. The workflow reference introduces this execution model.

Concern Saga Workflow

Process state

Persisted saga fields updated by handlers.

Step history and workflow payload; local control flow reconstructed during replay.

Event correlation

Association properties and values select saga instances.

Workflow identity and event-wait associations select the intended process and result.

Parallel work

Dispatch several commands, then join their outcome events with flags or counters.

Start non-blocking steps and waits, then combine their results with allMatch or anyMatch.

Timeouts

Schedule a deadline, store its identifier, handle expiry, and cancel it on success.

Configure a timeout on the step and branch on its outcome.

Retries

Persist an attempt counter and arrange the next attempt, often through a deadline.

Configure a step retry policy and backoff, or model a business retry loop explicitly.

Compensation

Store enough state to decide which effects must be undone in later handlers.

Express compensation around the relevant steps, preserving the same guards and failure handling.

Operational evidence

Inspect saga state, processor progress, and scheduled deadlines.

Inspect workflow and step histories as well as processor progress and external effects.

Workflow primitives make concurrency, timeout policy, retries, and compensation explicit in the process definition. They reduce the bookkeeping spread across handlers and provide step-level execution evidence. They do not infer business intent or make external effects exactly once. A retry can repeat an external call; use a stable idempotency key when that call must tolerate repetition. See step outcomes and retries, step orchestration, and workflow patterns.

Model the same process

Record the observable contract before selecting workflow primitives:

  • Which events start or advance the process, and how they are correlated.

  • Which commands and terminal events each path produces.

  • Which command results the saga observes, including failures it deliberately ignores.

  • Timeouts, attempt limits, compensation guards, and events accepted after another branch advances.

  • Duplicate, out-of-order, and late events, including updates to consumers when an event contract changes.

Compare success, rejection, failure, timeout, and restart traces against that contract. Register event waits before the command that can produce their event. Do not replace a dispatch-only command with a result-aware call without deciding how the newly observed failure should affect the process.

Some saga behavior has no equivalent in a proposed workflow, or cannot be represented by the available analyzer. Record such cases as unresolved or as explicitly accepted behavior changes. A shorter workflow is not evidence of equivalence. The skill process helps derive and check this model; it does not guarantee a direct conversion.

Example Shared business behavior

Parallel checks

Start credit and stock checks; join their first results in either order; accept only if both accept; each missing result expires as rejected after one day.

Approval timeout

Request approval; record approval if it arrives before expiry, otherwise expire after one hour.

Delivery retries

Attempt delivery up to three times after service exceptions, three seconds apart; record success or exhausted retries in the database.

Workflow service calls run inside durable steps; the process method contains the ordering, waits, and decisions. Service parameters on execute are supplied by Axon’s parameter resolvers; register the service implementations as Axon components or resolvable Spring beans. Application bootstrapping and service implementations remain application-specific; follow the workflow configuration guide to register the workflow definitions.

The saga examples compile against Axon Framework 4.12.1 and preserve the original deadline APIs for comparison. The workflow examples target Axoniq Framework 5.4.0. They are separate applications and must not share a Framework classpath. The selected AF5 legacy release does not provide the AF4 deadline API shown here; resolve that prerequisite using the existing legacy saga upgrade guide before coexistence.

Parallel steps

Both versions use the same ChecksService to start independent credit and stock checks. The service methods enqueue work and return without waiting for its result; both checks can be in progress together. Both versions accept the first result for each check in either order and ignore duplicate results. The saga publishes ChecksCompleted; the workflow completes naturally when both checks accept, or fails on rejection or timeout. The workflow does not publish a custom completion event. Consumers of ChecksCompleted therefore require a separate compatibility decision; the event contracts are not identical. Each check has one day to respond; a missing result counts as rejected. The saga joins both responses or expiries. The workflow can reject as soon as one wait times out, without waiting for the other deadline. The decision is accepted only when both results are accepted.

The saga stores result flags and deadline identifiers, cancels deadlines for received results, and joins results in separate handlers. The workflow registers the event waits, starts two durable service steps with ctx.execute, and joins the requests and results with ctx.allMatch. The step calls can execute concurrently; using awaitExecute for the first call would serialize the requests.

  • Saga (Axon Framework 4)

  • Workflow (Axoniq Framework 5)

public class ParallelChecksSaga {
    private String creditDeadline;
    private String stockDeadline;
    private boolean creditSeen;
    private boolean stockSeen;
    private boolean creditAccepted;
    private boolean stockAccepted;

    @StartSaga
    @SagaEventHandler(associationProperty = "orderId")
    public void on(ChecksRequested event, ChecksService checks, DeadlineManager deadlines) {
        creditDeadline = deadlines.schedule(Duration.ofDays(1), "credit-expiry", event.orderId());
        stockDeadline = deadlines.schedule(Duration.ofDays(1), "stock-expiry", event.orderId());
        // Request both operations without waiting for either result.
        checks.requestCreditCheck(event.orderId());
        checks.requestStockCheck(event.orderId());
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void on(CreditChecked event, EventGateway events, DeadlineManager deadlines) {
        if (creditSeen) return;
        deadlines.cancelSchedule("credit-expiry", creditDeadline);
        creditSeen = true;
        creditAccepted = event.accepted();
        finishIfReady(event.orderId(), events);
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void on(StockChecked event, EventGateway events, DeadlineManager deadlines) {
        if (stockSeen) return;
        deadlines.cancelSchedule("stock-expiry", stockDeadline);
        stockSeen = true;
        stockAccepted = event.accepted();
        finishIfReady(event.orderId(), events);
    }

    @DeadlineHandler(deadlineName = "credit-expiry")
    public void creditExpired(String orderId, EventGateway events) {
        if (creditSeen) return;
        creditSeen = true;
        finishIfReady(orderId, events);
    }

    @DeadlineHandler(deadlineName = "stock-expiry")
    public void stockExpired(String orderId, EventGateway events) {
        if (stockSeen) return;
        stockSeen = true;
        finishIfReady(orderId, events);
    }

    private void finishIfReady(String orderId, EventGateway events) {
        if (creditSeen && stockSeen) {
            events.publish(new ChecksCompleted(orderId, creditAccepted && stockAccepted));
            SagaLifecycle.end();
        }
    }
}
public class ParallelChecksWorkflow {
    @Workflow(workflowName = "ParallelChecks", workflowNamespace = "upgrade.examples",
              idProperty = "orderId", startOnEventClass = ChecksRequested.class)
    public void execute(SimpleWorkflowContext ctx, ChecksService checks) {
        String orderId = (String) ctx.workflowPayload().get("orderId");
        var order = associate(payloadProperty("orderId"), equalsTo(orderId));
        var credit = ctx.waitForEvent("credit", CreditChecked.class, order,
                step -> step.timeout(Duration.ofDays(1)));
        var stock = ctx.waitForEvent("stock", StockChecked.class, order,
                step -> step.timeout(Duration.ofDays(1)));

        // Start both requests before waiting for either one.
        var creditRequest = ctx.execute("requestCredit", (pc, input) -> {
            checks.requestCreditCheck(orderId);
            return input;
        });
        var stockRequest = ctx.execute("requestStock", (pc, input) -> {
            checks.requestStockCheck(orderId);
            return input;
        });
        if (!ctx.allMatch(WorkflowStepResult::success, creditRequest, stockRequest).success()) {
            ctx.fail(new StepFailedException("Both check requests must succeed"));
        }
        boolean accepted = ctx.allMatch(WorkflowStepResult::success, credit, stock).success()
                && credit.resultAs(CreditChecked.class).orElseThrow().accepted()
                && stock.resultAs(StockChecked.class).orElseThrow().accepted();
        if (!accepted) ctx.fail(new StepFailedException("Checks rejected or timed out"));
    }
}

CreditChecked and StockChecked carry the business outcomes in both versions, including rejected checks (accepted = false). Both joins use WorkflowStepResult::success directly. The result join succeeds after both results arrive; a timeout makes it return false. The business decision also requires both result payloads to contain accepted = true. Request methods must be idempotent using orderId, and each check must produce one authoritative result.

A rejected business result is still a successful event-wait step, so the result join waits for the other result. A failed or timed-out step short-circuits the join; it does not undo another branch’s external work. These examples perform read-only checks; reservation or payment branches need explicit handling for cancellation, compensation, and late success. See parallel steps and short-circuit behavior.

A step with a timeout

Both versions request approval and produce an approved result when confirmation arrives, or an expired result after one hour. The saga stores and cancels a deadline identifier. The workflow’s event wait carries the timeout and exposes its outcome directly. Both call ApprovalService.requestApproval, which enqueues the request and returns without waiting for approval. The workflow registers the wait before making this call inside a step, so a fast confirmation can be received.

  • Saga (Axon Framework 4)

  • Workflow (Axoniq Framework 5)

public class ApprovalSaga {
    private static final String EXPIRY = "approval-expiry";
    private String deadlineId;

    @StartSaga
    @SagaEventHandler(associationProperty = "orderId")
    public void on(ApprovalRequested event, ApprovalService approvals, DeadlineManager deadlines) {
        deadlineId = deadlines.schedule(Duration.ofHours(1), EXPIRY, event.orderId());
        approvals.requestApproval(event.orderId());
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void on(ApprovalReceived event, DeadlineManager deadlines, EventGateway events) {
        deadlines.cancelSchedule(EXPIRY, deadlineId);
        events.publish(new ApprovalCompleted(event.orderId(), true));
        SagaLifecycle.end();
    }

    @DeadlineHandler(deadlineName = EXPIRY)
    public void expired(String orderId, EventGateway events) {
        events.publish(new ApprovalCompleted(orderId, false));
        SagaLifecycle.end();
    }
}
public class ApprovalWorkflow {
    @Workflow(workflowName = "Approval", workflowNamespace = "upgrade.examples",
              idProperty = "orderId", startOnEventClass = ApprovalRequested.class)
    public void execute(SimpleWorkflowContext ctx, ApprovalService approvals) {
        String orderId = (String) ctx.workflowPayload().get("orderId");
        var approval = ctx.waitForEvent("approval", ApprovalReceived.class,
                associate(payloadProperty("orderId"), equalsTo(orderId)), step -> step.timeout(Duration.ofHours(1)));
        ctx.awaitExecute("requestApproval", ctx.workflowPayload(), (pc, input) -> {
            approvals.requestApproval(orderId);
            return input;
        });

        if (approval.success()) {
            ctx.awaitPublish("completed", new ApprovalCompleted(orderId, true));
        } else if (approval.timeout()) {
            ctx.awaitPublish("expired", new ApprovalCompleted(orderId, false));
        } else {
            ctx.fail(approval.error().orElseGet(() -> new StepFailedException("Approval wait failed")));
        }
    }
}

The workflow does not need a separate cancellation command for a wait that already completed. A timeout is a normal business outcome in this example, so the workflow publishes a negative result and completes. An unhandled StepFailedException fails the workflow; a failed event wait calls ctx.fail(…​).

Timing boundary: the hour begins when the saga schedules its deadline or the workflow registers its wait, not when an external user receives the request. Specify and test the policy for an approval racing with expiry and for an approval arriving after completion. A step timeout does not undo the external request. See event waits and workflow completion and failure.

Retry a failed service call

The saga stores an attempt counter and schedules a deadline three seconds after a failed service call. The workflow puts the delivery call in one durable step with a retry policy. Both allow three total attempts: the initial attempt plus two retries. Both call the same DeliveryClient and use the order identifier as its idempotency key. Both save delivered = true after success, or false after three failed calls. This example retries any exception from the delivery service, with the same limit in both versions. Both rely on the delivery client’s transport timeout; the client reports that timeout as an exception. Workflow service steps also have a five-second default timeout; configure it above the client’s transport timeout. A step timeout or cancellation leaves the delivery outcome unknown and requires reconciliation. The workflow performs that write in a separate durable step; it does not publish an extra delivery-completed event.

  • Saga (Axon Framework 4)

  • Workflow (Axoniq Framework 5)

public class DeliverySaga {
    private static final String RETRY = "delivery-retry";
    private int attempts;

    @StartSaga
    @SagaEventHandler(associationProperty = "orderId")
    public void on(DeliveryRequested event, DeliveryClient client,
                   DeadlineManager deadlines, DeliveryRepository deliveries) {
        attempt(event.orderId(), client, deadlines, deliveries);
    }

    @DeadlineHandler(deadlineName = RETRY)
    public void retry(String orderId, DeliveryClient client,
                      DeadlineManager deadlines, DeliveryRepository deliveries) {
        attempt(orderId, client, deadlines, deliveries);
    }

    private void attempt(String orderId, DeliveryClient client,
                         DeadlineManager deadlines, DeliveryRepository deliveries) {
        attempts++;
        boolean delivered;
        try {
            client.send(orderId);
            delivered = true;
        } catch (RuntimeException failure) {
            if (attempts < 3) {
                deadlines.schedule(Duration.ofSeconds(3), RETRY, orderId);
                return;
            }
            delivered = false;
        }
        deliveries.record(orderId, delivered);
        SagaLifecycle.end();
    }

}
public class DeliveryWorkflow {
    @Workflow(workflowName = "Delivery", workflowNamespace = "upgrade.examples",
              idProperty = "orderId", startOnEventClass = DeliveryRequested.class)
    public void execute(SimpleWorkflowContext ctx, DeliveryClient client, DeliveryRepository deliveries) {
        String orderId = (String) ctx.workflowPayload().get("orderId");
        var delivery = ctx.execute("deliver", (pc, input) -> {
            client.send(orderId);
            return input;
        }, step -> step.retryPolicy(RetryPolicy.maxRetries(2)
                .withBackoff(BackoffStrategy.fixed(Duration.ofSeconds(3)))
                .retryWhile(retry -> !(retry.error() instanceof StepTimedOutException))));
        if (delivery.timeout() || delivery.canceled()) {
            throw new StepFailedException("Delivery outcome unknown; reconcile before recording it");
        }

        boolean delivered = delivery.success();
        ctx.awaitExecute("recordDelivery", ctx.workflowPayload(), (pc, input) -> {
            deliveries.record(orderId, delivered);
            return input;
        });
    }
}

RetryPolicy.maxRetries(2) means two retries in addition to the initial attempt. The saga maintains an attempt counter and schedules retry deadlines; the workflow step applies the same retry limit and backoff. The database write follows the delivery outcome in both versions and is not part of the delivery retry loop.

Step retries rerun an action after a technical failure. A business retry driven by an event such as PaymentDeclined needs an explicit event wait and loop; a successful dispatch step does not fail merely because a later business event reports rejection. Preserve the original event contracts, backoff, attempt correlation, and cancellation behavior when modeling that loop. See retry policies and backoff.

Introduce workflows alongside legacy sagas

Keep existing instances in the saga runtime; route new starts to workflows. First verify the behavior inventory, accept intentional changes, and update affected consumers.

1. Prepare the coexistence deployment

Find the upgraded saga’s start handlers:

rg -n '@StartSaga|@SagaEventHandler' src/main/java

Remove only its @StartSaga annotations (including their imports):

-    @StartSaga
     @SagaEventHandler(associationProperty = "orderId")

Keep its handlers, command/event contracts, type identities, serialized fields, associations, stores, and processor identities unchanged. Associated instances still receive events; unmatched events no longer create sagas. Register the tested workflow using the workflow configuration guide. Deploy both changes together.

2. Pause, deploy, and resume

  1. Pause requests that start new processes. Existing sagas do not need to finish first.

  2. Stop all instances of the old application so they cannot start new sagas.

  3. Start the updated application with the existing saga handlers and the new workflow.

  4. Confirm that the workflow processor is ready and has saved its starting position before accepting new requests.

  5. Resume new requests: existing processes finish through sagas; new ones use workflows.

The saved position, called a token, is a bookmark in the event stream. A new workflow processor starts at the current end, leaving old start events with the sagas. Keep new requests paused until this bookmark is saved so they are not skipped. On later restarts, preserve the token and processor identity; resetting the position can duplicate or skip work. See initial tracking tokens.

3. Check both processes, then let old sagas finish

Test with persistent event, token, saga, and scheduler stores so state survives a restart:

  1. Before deploying, start one order and leave its saga waiting.

  2. Deploy the updated application. Confirm that the old order still uses its saga and that historical start events create no workflows.

  3. Start a new order and leave it waiting. Confirm that it creates exactly one workflow and no saga.

  4. Restart the application, then finish both orders. Both must resume and complete without missing events or repeating business actions.

Also test timeouts, retries, compensation, and duplicate or late events against the expected behavior. Keep the existing saga tests, but do not treat unit tests as proof that persistent recovery works. Fix any restart or persistence failures before proceeding.

Count the remaining sagas with a read-only query. Use your application’s table/column names and stored saga type; run separately for each tenant or add a tenant filter:

SELECT COUNT(*) AS remaining
FROM saga_entry
WHERE saga_type = 'com.example.orders.OrderSaga';

Wait for the count to reach zero and for commands, scheduled work, and failed/dead-lettered messages that need the saga to finish or be resolved. Track how long the oldest saga has been running; choose an observation period based on the process lifetime. Then follow Retire the drained legacy implementation.

If you roll back: keep the workflow definition and runtime available until existing workflows finish. Do not let sagas and workflows both start the same process. Test how new requests will be assigned during rollback, or fix the new deployment instead.

Retire the drained legacy implementation

Remove legacy code only after each upgraded saga type has no running instances or pending work depending on its handlers.

  1. Remove the drained saga type, its registration, and its dedicated deadline bridge. Preserve useful behavior assertions in workflow tests or an upgrade regression suite.

  2. Remove axoniq-legacy and axoniq-legacy-test only when no other saga or legacy feature requires them.

  3. Keep JPA and its transaction configuration when tokens, projections, or application data still use them.

  4. Prepare storage cleanup as a separate, reviewed schema change scoped to the retired type, tenant, and processor. Retain data required by recovery and retention policies.

Never drop a shared token table or remove workflow and projection tokens. Remove retired saga processor rows only after every deployment using that processor is gone. Shared saga, association, and scheduler tables may also serve other components.

Completion check: a fresh workflow completes and a waiting workflow resumes after restart without the retired legacy runtime. Other projections and processors retain their progress. Record drain evidence and the exact runtime components and storage objects removed.
